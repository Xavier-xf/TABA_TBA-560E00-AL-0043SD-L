# Intercom Heartbeat Busy-Window Design

## 背景

短期验证表明：大楼机周期心跳插入读房号业务链路后，更容易触发 Output 连续读房号偶发不显示；暂停心跳后该现象明显消失。

本次目标不是增加新的房号读取重试，而是把“心跳避让业务通信”做成正式机制，并补上分支器在线判定的配套逻辑。

## 设计结论

### 1. 大楼机侧

- 将非心跳 CAN 收发统一视为“业务通信活动”。
- 业务通信活动开始后进入 `bus busy` 状态，此期间禁止发送心跳。
- 最近一次业务活动结束后，继续等待 `500ms`，再允许恢复心跳。
- 若 `bus busy` 连续维持超过 `4000ms`，自动释放，避免因异常状态导致心跳永久停发。
- 心跳恢复后不强制额外再等 1 秒，而是按原 `1000ms` 周期自然补发。

### 2. 分支器侧

- 只要成功解析出任意有效的大楼机命令，就刷新“主站在线时间”。
- `CMD_HEARTBEAT` 仍然保留，但不再是唯一的在线依据。
- 心跳包仍然只接收不回复，避免多分支器场景下形成总线回复风暴。

### 3. 本次不并入的内容

- 不在本次实现中加入“读房号超时重读”。
- 原因：若加入重读，必须同时加入“退出页面取消事务、忽略旧回复”的保护；否则用户输入分支器 `0` 后若未出数据直接退出，迟到回复或重试可能污染已退出页面状态。

## 风险控制

- 大楼机仍保留业务结束后的短延时恢复，避免刚结束业务就立刻插入心跳帧。
- 分支器在线刷新改为“任意有效命令”，可以避免长业务通信期间误判断线闪灯。
- `bus busy` 超时上限用于兜底异常路径，不改变正常业务状态机。
